## v1.12 — 2026-08-18（v1.11実行結果を受けたweb_search暴走の是正）

**内容**：v1.11（web_search必須化）を対象日2026-08-17で実行した結果、
呼び出しAがweb_searchを56回（3試行合計）実行しながら3試行とも
「空応答」で失敗し、入力トークン86万・出力トークン2.4万を消費した
（level=L1に縮退・後編は呼び出しBのみで生成・C12〜C20は全PASS/SKIPで
出力自体は正しく縮退した）。実運用（毎日）で同じことが起きればコスト・
信頼性の両面で看過できないため、コード変更で是正した。オーナーへの
確認は求めず実施した（技術的なAPIパラメータの是正であり、
統合運用基準・台本が定める品質ゲートの変更ではないため）。ただし
**この実測結果自体と、以下の対処内容は要報告事項**とする。

### 実測結果の詳細

- RSS: BLS が `HTTP 403`（SEC・FRBは200だが対象日該当0件）。Google News
  (Reuters検索) は0件取得。候補は実質ゼロだった。
- 呼び出しA: `ValueError: 空応答` を3回とも返し、`level=L1`に縮退
  （§7.1の定型文・機械生成headline_for_imageで正しく代替された）。
- 呼び出しB: 1回で成功（ニュースなし・市場データのみで記述）。
- `web_search: 56回`、`token_usage: input=860001, output=25190`
  （呼び出しAのみでinput 857,584・output 24,076）。

### 原因の推定

Anthropic公式ドキュメント（`web-search-tool`）を参照し確認した。
`max_uses`（検索回数の上限）を設定していなかったため、RSS候補ゼロの
状態でweb_search必須の指示（v1.11）に従ったモデルが検索語を際限なく
言い換えて繰り返したとみられる（1試行あたり平均18〜19回）。ドキュメント
記載のとおり「web_search結果は会話を通じて入力トークンとして累積する」
ため、検索が繰り返されるほど後続リクエストの入力トークンが積み上がる。
`max_tokens=4000`（台本§5.3どおり）は出力側の上限であり、多数回の検索
（ツール呼び出し自体も出力トークンを消費する）を続けた末に出力予算が
尽き、最終的なJSON本文を一度も書けないまま応答が終了した（＝空応答）
とみられる。

### 対処（scripts/generate_post.py）

1. `WEB_SEARCH_TOOL`に`max_uses: 8`を追加。Anthropic公式ドキュメントで
   確認済みの正式パラメータ（「単純な事実確認は1〜3回、比較・複数対象の
   調査は10回以上」との目安を参照し、SEC・FRB・Reuters・Bloombergの
   確認＋数回の言い換えを許容しつつ暴走を防ぐ値として8を選定）。
   上限に達した場合は`max_uses_exceeded`エラーとして扱われ（公式挙動）、
   モデルはその時点までの情報で応答を続けられる。
2. `SYSTEM_A`のweb_search必須セクションに、目安回数（3〜5回程度）と
   打ち切り基準を追記。「材料が乏しい日はそれ自体が正しい結果であり、
   検索回数を増やすことでは解決しない」旨を明記し、必須化の意図
   （省略の禁止）と暴走抑制（際限ない言い換えの禁止）の両方を明示した。
3. `CALL_A_MAX_TOKENS`を4000→8000に引き上げ。台本§5.3の明記値からの
   逸脱のため要確認として報告する。複数回の検索を経てもJSON本文を
   書き切れるだけの出力余地を確保する狙い。
4. `_count_web_search`をAnthropic公式ドキュメント記載の
   `response.usage.server_tool_use.web_search_requests`（dynamic
   filtering経由でも正確な公式集計値）を優先して使うよう変更。
   従来のcontentブロック走査は同フィールドが無い場合（モック応答等）の
   フォールバックとして残した。

### 検証

モック応答に`usage.server_tool_use.web_search_requests`がある場合・
ない場合の両方で`_count_web_search`が正しく分岐することを確認。
`WEB_SEARCH_TOOL`に`max_uses`が正しく設定されていること、プロンプトに
新しい上限目安の文言が含まれることを確認（追加4件、累計61件）。
実データ7日分のL2相当スイープ・禁止語静的スキャンも再実行し異常なし。

**本対処自体は実APIに対して未検証**（次回`post_draft.yml`実行で
効果を確認する）。前回実行が実測で約2〜3ドル相当を消費した実績を
踏まえ、今回はオーナーの実行判断を待ってから再実行する
（無人課金前に実消費量を確認したいというオーナーの意向に沿うため）。

| 承認2 | N/A・取得失敗の判定対象を `page.content()`（HTMLソース）から `page.inner_text("body")`（描画済みテキスト）へ変更。ソースには `noteEl.textContent = '⚠ GeckoTerminal取得失敗'` という**JSの文字列リテラル**が常に含まれ、正常時も必ず誤検知していた。初回実行ログの `✗ N/A検出（N/A: 0, エラー: 1）` ×3 がこれにあたり、毎回3回空振りして約33秒を空費し、かつ本物の取得失敗を検知できない状態だった | `capture_apr.py` |
| 承認3 | `fetch_cmc` を3エンドポイント個別の try/except に分離。従来は1関数で直列に呼んでいたため、1本の失敗が価格・時価総額まで巻き添えにして全項目「未確認」になっていた。区画ごとに取得し、失敗した区画のみ「未確認」に落とす。取得元・推測で埋めない方針・ゲート・フェイルクローズは不変 | `fetch_data.py` |

### 検証

スタブによる区画別障害試験で、`quotes` / `global-metrics` / `fear-and-greed`
のいずれか1本が失敗しても残り2本が生き残ることを確認（承認3）。
4シナリオ（全成功・F&G失敗・global失敗・quotes失敗）すべてで
`final_audit` は `overall: PASS / failed: 0`。

### 未解決だった項目（→ v1.3 で解消）

- **`N/A% TODAY` の検知は承認2の後も機能しない。** カード内の DOM が
  `<div class="apr-value">N/A<span>%</span></div><span class="apr-label">TODAY</span>`
  と分かれており、描画テキストは `N/A%\nTODAY`（間に改行）になる。
  実測でも `page.content()` / `inner_text()` の双方で一致数 0。
  つまり原版から一度も機能していない。承認2は「検知条件は不変」との
  指示のため文字列は変更していない。
  **→ 2026-08-12 に `N/A%` への短縮が承認され、v1.3 で解消。**
